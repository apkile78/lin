1. CPU ARCHITECTURE FRAMEWORK
----------------------------------------------------------------
- A generic CPU interface is exposed to the rest of the emulator
  (memory manager, device bus, boot orchestration):
    step()
    readRegister(name) / writeRegister(name, value)
    raiseInterrupt(vector)
    getMode() / setMode()
  The rest of the system only ever talks to this interface — it
  never needs to know which architecture is actually running.

- Architecture-specific logic (decode tables, register file shape,
  flag semantics) lives BEHIND this interface, in swappable
  per-architecture modules. Adding a new architecture later (e.g.
  ARM) means writing one new module — no changes to the rest of
  the emulator.

- x86_64 and x86_32 are ONE shared module, not two separate
  implementations — 32-bit is a MODE of the 64-bit core, matching
  real hardware and BIOS/bootloader compatibility expectations.

- 16-bit REAL MODE is a first-class mode the decoder must support,
  because firmware (section 3) actually executes as real-mode code
  on this CPU core. Segment:offset addressing, real-mode default
  operand/address sizes, and the real-mode interrupt vector table
  at address 0 are all required.

- EXECUTION SPEED / INTERPRETER DESIGN (resolves external review
  item: pure interpreted JS may be far too slow to boot Windows —
  a naive interpreter lands around 5-20 MIPS; Windows boot involves
  hundreds of millions to billions of executed instructions):
    * CONFIRMED: the CPU core's inner step() loop is written in a
      WASM-PORTABLE STYLE FROM DAY ONE — plain arithmetic,
      typed-array/DataView memory access over the SharedArrayBuffer,
      a dispatch-table opcode lookup (array of function references
      indexed by opcode) instead of a switch statement, no objects
      allocated per instruction, no JS-only closures/features in
      the hot path. This is done even before performance is proven
      to be a problem, so a later WASM port is mechanical rather
      than a rewrite.
    * THREE-TIER PLAN:
        Tier 1 — disciplined WASM-style JS interpreter (build
                 first; correctness priority, matches the plan's
                 "correct first" pattern used throughout)
        Tier 2 — compile the hot decode+execute loop to WASM
                 (AssemblyScript / hand-written WAT / Emscripten),
                 once Tier 1 is MEASURED too slow, not assumed to be
        Tier 3 — JIT / dynamic binary translation (compile basic
                 blocks of guest code into cached JS/WASM functions,
                 as v86 and QEMU's TCG do), ONLY if Tier 2 is
                 empirically insufficient for the Windows-boot goal
                 specifically — a project-sized undertaking on its
                 own, not built preemptively

- Full x86 integer instruction set (category summary):
    Data movement: mov, push, pop, lea, xchg, movzx/movsx, cmovcc
    Arithmetic: add, sub, adc/sbb, mul/imul, div/idiv, inc/dec,
                neg, cmp
    Logic/bitwise: and, or, xor, not, shl/shr, sar, rol/ror,
                   bt/bts/btr
    Control flow: jmp + all jcc conditional variants (~30), call,
                  ret, loop, int
    Stack/frame: push/pop, enter/leave
    String/memory block ops: movs, stos, cmps, scas, lods
                              (with rep/repne prefixes)
    Privileged/system (ring 0): cli/sti, hlt, lgdt/lidt,
                                 mov to/from CR0-CR4, in/out, iret

2. MEMORY MODEL — x86 MMU
----------------------------------------------------------------
DECISION: Built fully self-contained (Option A) — x86's MMU
(segmentation + paging together), not built on a shared generic
MMU module. A generic/shared MMU abstraction will only be
extracted later, once a second real architecture implementation
(e.g. ARM) exists to generalize from.

Two-layer x86 memory model:

  A) SEGMENTATION (mostly vestigial in 64-bit long mode, fully
     active/required in 32-bit protected mode)
     - Segment registers: CS, DS, SS, ES, FS, GS
     - GDT: array of 8-byte descriptors (base, limit, access/flags)
     - 32-bit mode: segment register -> GDT entry -> limit check ->
       add segment base to linear address BEFORE the paging walk
     - Long mode: segment bases mostly forced to 0, limits ignored
       — EXCEPT FS/GS, still needed for thread-local storage

  B) PAGING
     - Page table walker: virtual address + CR3 + mode -> walks
       2-level (32-bit) / 3-level (PAE) / 4-level (long mode)
       tables, checking PRESENT and permission bits at each level
     - Mode-dependent table format, branches on current mode

TLB (translation cache) — REVISED after external review:
  - ORIGINAL PLAN was an unbounded Map (no eviction). REVISED to
    BOUNDED/LRU after external review flagged unbounded host memory
    growth risk over long-running guest sessions (processes
    spawning/terminating repeatedly).
  - CONFIRMED: capped entry count (~1024-4096 entries), LRU
    eviction. Implemented via a Map's insertion-order semantics:
    on a hit, delete+reinsert the entry (moves it to the
    "most-recently-used" end); on a miss requiring insertion, if
    size exceeds the cap, delete the first key in iteration order
    (least-recently-used) before inserting.
  - KEYED BY (CR3, virtual page number) — unchanged, this
    composite key is independent of the eviction policy change and
    still avoids losing all cached translations on every CR3
    switch (approximates what real hardware's PCID achieves).
  - CONFIRMED: ONE TLB INSTANCE PER VIRTUAL CORE (not shared across
    cores) — matches real hardware, avoids any cross-core TLB
    synchronization concern.
  - invlpg uses the CURRENT CR3 as half the key:
    Map.delete((currentCR3, thatVirtualPage))
  - FAITHFUL HARDWARE REPLICATION for invalidation: guest OS must
    call invlpg correctly, exactly like real hardware. No
    auto-detection of stale entries on page table edits.

Page fault (interrupt 14) generation:
  - Triggered on: page not present, OR permission violation
  - Must set CR2 to the faulting virtual address
  - Must push an error code with exact bit meanings:
      bit 0 = present/not-present   bit 1 = read/write
      bit 2 = user/supervisor       bit 3 = reserved-bit violation
      bit 4 = instruction fetch
    Guest kernels' fault handlers decode these bits exactly.

3. FIRMWARE / BIOS LAYER
----------------------------------------------------------------
DECISION: Firmware is built as REAL 16-bit real-mode code that
EXECUTES ON THE EMULATOR'S OWN CPU CORE — authentic, like real
BIOS/SeaBIOS — not faked/intercepted in host JavaScript.
  - The faked/intercepted-in-JS approach MAY be added later as an
    optional "BIOS optimization mode" toggle, not primary design.
  - Authoring approach (hybrid): Pi writes the real-mode firmware
    code by hand, referencing existing open-source BIOS
    implementations (e.g. SeaBIOS) for calling-convention/
    behavioral logic — not copying code, using it as reference only.

Two boot paths:
  1) DIRECT-INJECT — bypasses firmware entirely. Boot shim loads a
     kernel binary directly, sets CR3/GDT/paging manually, jumps
     to the kernel entry point per the Linux boot protocol.
     Fastest/simplest. Default for Linux.
  2) FULL-FIRMWARE — CPU starts at reset vector (0xFFFF0, real
     mode) -> firmware runs -> reads MBR/GPT -> loads the real
     bootloader (GRUB or Windows Boot Manager), which takes over,
     calling back into firmware's INT 13h/10h handlers as needed.
     REQUIRED for Windows. Optional realistic path for Linux (GRUB,
     enables booting unmodified install ISOs).

Firmware internals:
  - Reset vector: jmp at 0xFFFF0 into firmware entry code
  - INT 13h (disk): CHS/LBA -> offsets into the IndexedDB-backed
    virtual disk
  - INT 10h (video): text-mode output to 0xB8000, mode-setting
  - INT 15h (E820 memory map): describes available RAM regions
  - MBR emulation: reads sector 0 into 0x7C00, verifies boot
    signature, jumps to it

LEGACY BIOS vs UEFI:
  DECISION: Both legacy BIOS and UEFI are planned (not
  legacy-only) — needed because modern Windows (8+) defaults to
  UEFI boot.
  DECISION: FULLY INDEPENDENT implementations, selected as a
  setup-time either/or choice per VM config — not a shared/unified
  abstraction, since they share almost nothing architecturally.

  UEFI specifics:
    - No interrupt-based services — exposes a table of FUNCTION
      POINTERS (Boot Services, Runtime Services)
    - Runs in 32/64-bit protected/long mode from the start, not
      16-bit real mode — a separate boot flow from legacy BIOS
    - Disk layout: GPT + EFI System Partition (FAT32), bootloader
      as a .efi PE-format executable
      (Windows: \EFI\Microsoft\Boot\bootmgfw.efi)
    - Core pieces: GPT parser, minimal FAT32 driver, PE/COFF
      loader, UEFI Boot Services table implementation
      (AllocatePages, LocateProtocol, ExitBootServices, etc.),
      UEFI Runtime Services (variable services, time services)

  ACPI TABLES + CPUID (added after external review — Windows UEFI
  boot strictly depends on these, will fail/BSOD without them):
    - Required ACPI tables:
        RSDP  — entry point UEFI hands to the OS
        XSDT  — pointer table to all other ACPI tables
        FADT  — power management info, boot flags Windows checks
                early
        MADT  — core count + Local APIC IDs; TIES DIRECTLY TO THE
                MULTI-CORE DESIGN (section 7) — Windows learns
                core topology from this table, not by probing
                hardware
        HPET  — high-precision timer description; modern Windows
                prefers this over PIT for high-res timing
    - CONFIRMED: ACPI tables are GENERATED DYNAMICALLY PER VM
      CONFIG (not a fixed/hardcoded layout) — built once per VM
      at boot time from that VM's actual vCPU count and RAM size,
      matching the variable-vCPU/vRAM-per-config design. More
      upfront implementation work than a static table, chosen
      deliberately to avoid a real mismatch once VMs with different
      core counts exist.
    - CPUID: must report CMPXCHG16B, the NX/XD bit, LAHF/SAHF (long
      mode), and SSE2/SSE3 as present, or Windows will immediately
      BSOD with UNSUPPORTED_PROCESSOR. Declaring these is accurate
      as long as the corresponding instructions are genuinely
      implemented (they are, per the full instruction set).

4. FPU / SIMD
----------------------------------------------------------------
DECISION: Full x87 + SSE + AVX planned now, not deferred.
DECISION: x87, SSE, and AVX are THREE SEPARATE internal register
files/decode tables within the x86 module, not part of the generic
CPU interface (ARM has nothing resembling x87's stack model).

x87 FPU: 8 registers (ST0-ST7) as a STACK, tag word tracking
validity, 80-bit extended precision internally, control/status
words (rounding mode, exception masks, condition codes).
Instructions: fld/fst, fadd/fsub/fmul/fdiv, fcom, transcendentals
(fsin/fcos/fsqrt), stack management (ffree/fxch).

  PRECISION DECISION (phased, easier first) — REVISED STAKES after
  external review: build the 64-BIT JS-DOUBLE APPROXIMATION first
  (simpler, gets the dispatch/pipeline correct before chasing
  precision bugs). TRUE 80-BIT EXTENDED PRECISION is a later
  upgrade pass — BUT external review flagged that the 64-bit gap
  can cause real GUEST KERNEL PANICS during driver initialization,
  not just cosmetic rounding differences. CONFIRMED: the 80-bit
  upgrade is now a HARD GATE — required before the first real
  Windows boot attempt, and before any driver/userspace-heavy
  Linux boot — not "later, whenever," but an explicit prerequisite
  milestone.

SSE: 16 registers (XMM0-15 in 64-bit, 8 in 32-bit), 128 bits each,
FLAT (not stack-based). Packed data (4x32-bit float / 2x64-bit
float / packed integers) — instruction determines interpretation.
Instructions: movaps/movups, addps/addss, comparisons,
shuffle/pack/unpack, int/float conversions.

AVX: extends XMM to 256-bit YMM registers (low 128 bits of YMM IS
the corresponding XMM register, same physical storage). Introduces
the VEX prefix — a genuinely different, three-operand encoding
scheme requiring a real second decoder path, not just more opcodes.

5. OS-SPECIFIC BOOT PATHS
----------------------------------------------------------------
LINUX — two paths:
  1) Direct-inject (default fast path, section 3)
  2) Full-firmware via GRUB — reset vector -> real-mode firmware
     -> MBR/GPT -> GRUB runs AS REAL-MODE CODE ON THE CPU CORE ->
     loads kernel+initrd via INT 13h -> GRUB switches to protected
     mode -> jumps to kernel. Enables booting unmodified Linux
     install ISOs without special preparation.

WINDOWS — full-firmware only, no shortcut exists:
  - Windows Boot Manager (bootmgr) requires real firmware services
  - Sequence: reset vector -> firmware -> MBR/GPT -> Windows Boot
    Manager -> reads BCD -> loads winload.exe/winload.efi -> loads
    ntoskrnl.exe and drivers
  - BOTH legacy BIOS and UEFI paths supported (modern Windows
    defaults to UEFI)

  - gh-pages branch for immediate testing; GitHub Releases as
    manual opt-in for permanent artifacts; binaries never committed
    to the main repo

7. DEVICE MODEL + MULTI-CORE
----------------------------------------------------------------
Disk controller: IDE/ATA first (simple, universal), AHCI later as
an option. Both backed by the chunked IndexedDB virtual disk
(section 9).

Input: 8042 PS/2 controller emulation (keyboard scancodes + mouse)
for universal driver compatibility.

Timer: PIT as baseline (drives OS tick/scheduler), RTC for
wall-clock time, APIC timer deferred.

Video: VGA text mode (0xB8000, firmware/early boot) plus a linear
framebuffer mode (canvas-rendered) for the graphical desktop phase.
Mode switch via INT 10h / VBE-style calls.

Interrupt controller: PIC (8259) as baseline; APIC/IOAPIC REQUIRED
(not deferred) because multi-core is built in from day one.

MULTI-CORE / MULTI-VCPU:
  DECISION: BOTH single-vCPU (default) AND full multi-core support
  are in scope. DECISION: multi-core is INTEGRAL FROM DAY ONE —
  Worker/SharedArrayBuffer/APIC plumbing exists from the start;
  single-core is simply the N=1 case. No phased/incremental
  approach — this was explicitly confirmed as "no second pass."

  How cores share the machine:
    - Each vCPU core is a separate instance of the CPU module (own
      registers/decode state), all sharing the SAME memory space
      and SAME MMU/page tables
    - Each vCPU driven by a SEPARATE WEB WORKER
    - Shared RAM backed by a SharedArrayBuffer

  SharedArrayBuffer / COOP-COEP — RESOLVED:
    - GitHub Pages can't natively set the required COOP/COEP
      headers. RESOLVED via the coi-serviceworker client-side
      workaround (intercepts fetches, injects headers via a
      service worker) — the SAME approach Pi already has proven
      working in the cdda-web-build project. No new research
      needed.
    - NOTE (from external review): coi-serviceworker requires an
      initial page fetch to register before forcing a reload to
      inject the headers. First-time visitors will see ONE
      mandatory reload before SharedArrayBuffer becomes available
      (window.crossOriginIsolated). This is expected, documented
      behavior, not a bug to engineer around.

  TSO / MEMORY ORDERING (added after external review — x86
  guarantees Total Store Order across cores; SharedArrayBuffer
  access is UNORDERED by default unless wrapped in Atomics, so
  plain reads/writes across Worker threads risk real race
  conditions that don't exist on real hardware):
    - CONFIRMED pragmatic approach: every LOCK-prefixed instruction
      (lock cmpxchg, lock xadd, lock inc, lock or, etc.) and
      explicit fence instruction (mfence/lfence/sfence) is mapped
      1:1 to the matching Atomics.* call (Atomics.compareExchange,
      Atomics.add, etc.)
    - Ordinary (non-synchronization) loads/stores remain PLAIN FAST
      ARRAY ACCESS, not given blanket Atomics-level ordering —
      avoids a severe performance tax on every memory access, since
      real guest kernels only rely on ordering for lock/fence-based
      synchronization, not ordinary memory access

  IPIs: each virtual core has its own Local APIC; a shared IOAPIC
  routes device interrupts to the correct core. Real protocol work
  — APIC has its own register interface and delivery modes.

  MMU/TLB implication: the (CR3, page) composite TLB key already
  composes cleanly with multi-core — each core's TLB stays correct
  even with different cores running different processes
  simultaneously, since CR3 is already part of the cache key.

8. MULTI-INSTANCE ARCHITECTURE
----------------------------------------------------------------
MULTIPLE TABS: each browser tab is already a fully isolated JS
environment — falls out for free, no cross-tab coordination code
needed. Only requirement: VM state/config must be saveable/
reloadable (storage layer, section 9) so a second tab starts a
DIFFERENT VM instance.

ONE TAB, multiple switchable VM configs: a VM MANAGER layer tracks
configs and active/suspended state. Only ONE VM instance actively
runs (consumes CPU/Worker cycles) per tab at a time.

DECISION: suspended VMs are KEPT ALIVE BUT IDLE — Worker threads
stay allocated, simply stop calling step(). Trivially/instantly
resumable. Tradeoff knowingly accepted: each suspended VM continues
holding its full Worker pool and memory allocation while idle;
multiple suspended VMs means multiple full idle memory allocations.
Chosen deliberately over full-termination-and-reserialize (cheaper
on resources, but slower to resume and requires clean serialize/
deserialize logic for every piece of CPU/device state).

Architectural shape:
    Tab
     └── VM Manager (tracks configs, active/suspended state)
          ├── VM Instance A (active)    — N Worker-backed vCPUs,
          │                               SharedArrayBuffer RAM,
          │                               devices, all running
          ├── VM Instance B (suspended) — Workers alive, idle
          └── VM Instance C (suspended) — Workers alive, idle

9. STORAGE DESIGN
----------------------------------------------------------------
IndexedDB object stores:
  - os-images    — base OS/kernel/firmware artifacts (shared,
                    read-only reference copies across VM instances)
  - vm-configs   — per-VM metadata: OS, architecture, firmware type
                    (BIOS/UEFI), vCPU count, RAM size, disk size
  - vm-disks     — per-VM virtual hard disk contents (likely the
                    largest storage consumer)
  - vm-snapshots — full CPU+RAM+device state for resuming a VM
                    across a full BROWSER RESTART (not just a
                    tab-switch, which the kept-alive-but-idle
                    approach in section 8 already handles)

DECISION: vm-disks storage is CHUNKED FROM THE START — e.g. 4-16MB
records per virtual disk, with a chunk-index/mapping layer
translating "virtual disk sector N" to "which IndexedDB record
holds it." NOT single-blob-per-disk.
  - Rationale: large blobs (a multi-GB Windows disk image) hit
    practical size hiccups in some browsers as one giant blob, and
    a single-blob approach means potentially serializing the ENTIRE
    disk on every write. Chunking keeps partial writes cheap
    regardless of how large disks grow.

10. NETWORKING — REVISED: FUTURE PROJECT-ROOT NEED, NOT CUT
----------------------------------------------------------------
REVISED DECISION (originally "cut entirely, not even a later
phase"): Pi now expects real guest-OS networking will likely
become a PROJECT-ROOT need in the future — i.e. not merely a
nice-to-have deferred feature, but something the project is
expected to eventually require as core functionality.

Why real networking is architecturally hard, unchanged from the
original analysis:
  - No browser context (main thread, Web Worker, Service Worker,
    or WASM running in any of them) has access to raw TCP/UDP
    sockets — this is a deliberate, permanent, universal browser
    security boundary, not a gap that will be filled by future
    browser versions, and WASM does not escape it (only WASI
    runtimes OUTSIDE a browser, like wasmtime, can do real sockets)
  - The ONLY functions any browser JS/WASM context can use to move
    bytes anywhere outside the page: fetch(), XMLHttpRequest,
    WebSocket, WebRTC — the complete list, nothing else exists
  - A managed Chromebook additionally blocks every on-device
    workaround (no Crostini, no Developer Mode, no extension
    sideloading, no native app installation)

THE PLANNED APPROACH (when this is built): a small backend hosted
on RENDER (or similar — Fly.io, a VPS) acting as a
WebSocket-to-real-TCP/UDP proxy:
    Guest OS (virtual NIC, believes it's on a real network)
       -> emulator's NIC-emulation JS (in a Worker, ideally, to
          avoid janking the main thread)
       -> WebSocket connection to the Render-hosted proxy
       -> proxy performs REAL connect()/send() calls on the
          guest's behalf (ordinary Node/Python process, no browser
          sandbox restrictions apply to it)
       -> real internet destination
  - This is a real, small piece of ALWAYS-ON INFRASTRUCTURE that
    must be deployed and maintained separately from the static
    GitHub Pages site — a genuine addition to project scope,
    accepted deliberately now that networking is a project-root
    goal rather than being cut
  - Free tiers exist (Render's free tier "sleeps" after ~15 min of
    inactivity — first connection after that has a several-second
    wake-up delay; acceptable tradeoff for occasional use)

What works WITHOUT any networking (unaffected either way): any
single-player game/app with no online features, local file
operations, installs from local/sideloaded media, anything using
only hardware abstractions (audio, input, video, clock/timer).

What NEEDS networking (the reason it's becoming project-root):
multiplayer/online games, DNS lookups, runtime downloads from
inside the guest (package managers, curl/wget, launcher "check for
updates"), NTP sync, SSH in/out of the guest, any client-server app
relying on live network access.

STATUS: This is a directional decision (networking WILL be needed
eventually, and the Render-proxy approach is the confirmed
mechanism), but detailed design (protocol between guest NIC and
proxy, exact scope of what needs proxying, when in the build
sequence this gets tackled relative to sections 1-9) has NOT yet
been revisited/re-planned since this correction — treat this
section as directional, not fully detailed, pending a dedicated
planning pass.

12. EXTERNAL FEASIBILITY REVIEW — RESOLUTION SUMMARY
----------------------------------------------------------------
An external AI review of this plan raised six concrete risks.
Resolution status of each:

  1. Execution speed (interpreted JS too slow for Windows boot)
     -> RESOLVED: see section 1 (WASM-portable style from day one,
        three-tier upgrade plan: interpreter -> WASM hot loop ->
        JIT if needed)

  2. Unbounded TLB memory growth over long sessions
     -> RESOLVED: see section 2 (bounded/LRU, ~1024-4096 entries,
        per-core, composite key unchanged)

  3. x86 TSO not automatically provided by SharedArrayBuffer;
     LOCK-prefixed opcodes need explicit Atomics mapping
     -> RESOLVED: see section 7 (lock/fence instructions mapped
        1:1 to Atomics.*, ordinary access stays plain/fast)

  4. x87 80-bit vs 64-bit precision gap risks real kernel panics,
     not just cosmetic inaccuracy
     -> RESOLVED: see section 4 (80-bit upgrade is now an explicit
        hard gate before Windows/heavy-Linux boot attempts, not
        soft "later" polish)

  5. UEFI Windows boot needs real ACPI tables and correct CPUID
     flags or Windows will BSOD
     -> RESOLVED: see section 3 (RSDP/XSDT/FADT/MADT/HPET,
        generated dynamically per VM config; required CPUID bits
        identified: CMPXCHG16B, NX/XD, LAHF/SAHF, SSE2/SSE3)

  6. coi-serviceworker requires an initial reload before
     SharedArrayBuffer becomes available (first-visit UX hit)
     -> RESOLVED: see section 7 (documented as expected one-time
        behavior, no design change needed)

Suggested phased testing milestones from that review (not yet
formally adopted into the build sequence, but a reasonable
reference order):
  Milestone 1: Real-mode boot — FreeDOS or a minimal sector
               bootloader with INT 10h output
  Milestone 2: Protected-mode GDT/paging — custom Linux kernel via
               direct-inject
  Milestone 3: SharedArrayBuffer atomics + IOAPIC routing — dual-
